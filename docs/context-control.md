# 上下文膨胀治理方案

> 结论先行：**不是系统提示词或工具清单太大，是工具产出无节制地永久驻留在 history 里；而现有的两道防线（自动压缩、消息数裁剪）都是"按回合"的粒度，管不到"一个回合内跑几十轮工具"这种真实形态。**

本方案基于一份真实落盘上下文的逐条测量，不是推测。取证样本：
`%AppData%\runcode\context-audit\sess_fa6781da5038d4d2.jsonl`（22.9 MB，51 次请求）。

## 一、测量事实

### 1.1 总体

| 指标 | 值 |
| --- | --- |
| 请求数 | 51（47 次 assistant + 6 次 harm_check/session_title 旁路） |
| 累计发出字节 | 21.4 MB |
| 单次最大请求 | 630,527 B ≈ **146,581 est. tokens** |
| **第一次**请求就已经 | 84,403 est. tokens / 44 条消息 |
| 用户消息数 | **3 条** |
| 最终 history 消息数 | 124 条 |

**"只有两段对话却爆了"的原因**：3 条用户消息切出 3 个回合，消息分布是 `[43, 60, 21]`。
也就是**第一个回合还没等到用户第二次说话，就已经堆到 84K tokens**；第二个回合一口气 60 条消息。

### 1.2 成分（最终 history，按估算 token）

| 类别 | est. tokens | 占比 |
| --- | --- | --- |
| `tool_result` | 106,575 | **75.7%** |
| `tool_use`（工具入参） | 24,969 | **17.7%** |
| `thinking` | 7,065 | 5.0% |
| `text`（助手正文） | 2,112 | 1.5% |

系统提示词 10 个 block 共 12,913 B + 工具 schema 8,638 B = **21.5 KB（约 5.4K tokens，3.5%）——常量，不是问题所在**。
优化系统提示词对这个案子毫无意义。

### 1.3 单项最大头

前 4 项就占了整个请求的 **45.8%**：

| 字节 | 来源 |
| --- | --- |
| 99,266 | `Read` ppt-master/references/strategist.md |
| 66,261 | `Skill` ppt-master（SKILL.md 本体） |
| 61,829 | `Read` references/shared-standards.md |
| 51,231 | `Read` references/executor-base.md |

按工具聚合：`Read` 29 次 = 355,724 B（均值 12 KB/次）；`Write` 16 次的**入参**= 94,607 B（均值 5.9 KB，都是完整 SVG/Markdown 正文，写完仍永久留在上下文里）。

### 1.4 浪费与重复

- `spec_lock.md` 同一范围被读 **4 次**（各 ~2 KB）；同一条 permission denied 结果重复 **11 次**；`"File written."` 重复 16 次。合计约 6 KB —— 字节不多，但说明**没有任何去重/退役机制**。

### 1.5 压缩为什么一次都没生效

阈值是 `0.8 × 128,000 = 102,400` tokens。**第 7 次请求就已越线（119,897），此后连续 44 次请求全部越线。** 但压缩一次都没发生：

```
compaction.DefaultKeepRecentTurns = 4
turns = 3  →  len(turns) <= keep  →  Compact() 原样返回 history
```

`maybeCompact` 每个回合结束都被调用、每次都判定"没有回合可以退役"，于是 44 次越线全部空转。

## 二、根因（代码级，全在 `../agentloop`）

| # | 位置 | 问题 |
| --- | --- | --- |
| R1 | `internal/repl/session.go:636`（`commitTurn` → `maybeCompact`） | 压缩**只在回合结束**检查。本案一个回合 60 条消息 / +60K tokens，回合内无人干预。 |
| R2 | `internal/compaction/compact.go:17,102` | 压缩单位是"回合数"。`DefaultKeepRecentTurns=4`，回合数 ≤ 4 直接返回。编码代理的单个回合体积无上界，**回合数是错误的计量单位**。 |
| R3 | `internal/repl/history_trim.go:32` | `remaining := budget - len(mandatory)`，`mandatory` = 当前回合全部消息，**结构上不可能压住回合内增长**。且桌面默认 `MaxHistoryMessages = 0`（关闭，见 `internal/desktop/store.go:30 defaultRequest()` 只设了 `MaxContextTokens`）。 |
| R4 | `internal/repl/tool_result.go:18`（`ToolResultBlock`） | 工具结果**原样**转成 content block，无上限。`tools/read/read.go` 的单次上限是 2000 行 / 200,000 B —— 对"一次性查看"合理，对"永久驻留上下文"过于宽松。 |
| R5 | 无 | `tool_use` 入参永不退役。`Write` 的正文写完就落盘了，上下文里那份是纯死重。 |
| R6 | `internal/repl/session.go:956` | `maybeCompact` 依赖 `usage.InputTokens`（上一次调用的 provider 回报值）：晚一步，且 usage 为 nil 时静默关闭整条防线。而 `internal/repl/context_estimate.go` 里**已有**本地估算器 `estimateRequestTokens`，却只用来给恢复会话时的 UI 进度条打底，从未参与循环控制。 |

一句话概括架构缺口：**上下文管理是"回合粒度"的，而代理干活是"迭代粒度"的；且 history 只增不减 —— 一段内容一旦进去，永远按原价计费。**

## 三、方案：分层，从确定性到昂贵

设计原则（对应 CLAUDE.md）：优先做**确定性、无需额外 LLM 调用、不破坏 prefix 缓存**的层；把需要 LLM 的压缩留到最后兜底。

### ⚠️ 准入条件一：可确定性复原（防止丢失关键内容）

**只有存在确定性复原路径的内容才允许脱水。** 按此分类实测（见 §1.2 同一份 history）：

| 类别 | est. tokens | 占比 | 处置 |
| --- | --- | --- | --- |
| 可复原的结果（Read/Glob/Grep/Skill/TodoWrite） | 101,789 | 72.3% | 可脱水（重读即得） |
| 可复原的入参（Write/Edit，正文已落盘） | 24,080 | 17.1% | 可脱水 |
| 助手推理/正文（thinking/text） | 9,177 | 6.5% | **从不触碰** |
| **不可复原的结果**（Bash 4,639 / AskUser 117 / open_preview 30） | 4,786 | **3.4%** | **永不截断**，只能交给 L3 摘要 |
| 不可复原的入参 | 889 | 0.6% | **永不截断** |

不可复原 = 重跑未必复现、或有副作用、或是用户自己说的话：`Bash` 输出（构建/测试错误）、`WebFetch`/`WebSearch`（网络状态已变）、`AskUser` 答复、权限决定、用户消息本身。
**把这 4% 全额豁免，收益一分不少** —— 这是"不丢关键内容"的结构性保证，而非靠调参。

另加两条硬规则：**用户消息与 AskUser 答复永不脱水、永不摘要**；脱水设年龄下限，**绝不碰当前迭代的结果**。

### ⚠️ 准入条件二：按"年龄"脱水，不在"到达时"截断

实测三种做法在同一份请求上的结果：

| 做法 | est. tokens | 占基线 |
| --- | --- | --- |
| A：入库即截 8KB | 48,914 | 34.8% |
| B：入库 64KB 仅作防护 + 陈旧(>16 条)脱水到 8KB | 48,914 | **34.8%** |
| C：完全不设入库上限 + 陈旧脱水到 8KB | 48,914 | **34.8%** |

**三者完全相同。** 因为所有大块负载到末尾都已陈旧 69–122 条消息：

```
24,092 tokens  msg[ 36]  Read   age= 88 条消息
16,244 tokens  msg[  2]  Skill  age=122 条消息
14,596 tokens  msg[ 55]  Read   age= 69 条消息
12,450 tokens  msg[ 55]  Read   age= 69 条消息
```

结论：**激进的入库截断换来零额外收益，却承担全部风险** —— 截掉模型当下正在推理的文档。因此入库上限只作**高位防护**（~64 KB，防某个 MCP 返回 1 MB 打穿窗口，正常永不触发），真正的活由**年龄驱动的脱水**来干。

### ⚠️ 贯穿全案的关键取舍：prefix 缓存

用户当前走 OpenAI 兼容端点（`llm/providers/openai/provider.go:117` `SupportsCacheControl: false`），缓存是**服务端按前缀自动命中**的。因此：

- **L1 是"入库前截断"，从不改写已有前缀 → 缓存安全，可以一直开。**
- **L2/L3 会改写历史前缀 → 必然让后续请求缓存全失效。** 所以它们**只能在离散的、有阈值的压缩事件上触发，绝不能每轮迭代持续改写**——否则每轮都缓存未命中，省下的钱不如多花的。策略是：一次性付一次未命中，换一个更小且此后稳定的前缀。

### L0 — 让预算成为随时可用的一等信号（前置，零成本）

把 `estimateRequestTokens` 从"恢复时给进度条打底"提升为**循环控制信号**：每轮迭代构造请求前即可算出预算占用。再用 provider 回报的真实 `InputTokens` 做校准（`reported/estimated` 的 EMA 比值），让估算按模型自我修正。纯函数，无 LLM，无网络。

R6 顺手修掉：usage 为 nil 时改用估算值，而不是关闭防线。

### L1 — 入库上限，仅作高位防护（确定性 / 无 LLM / 缓存安全）

在唯一的收口处 `ToolResultBlock` 给每条工具结果设一个**高位**上限（~64 KB），只为防止单个工具/MCP 返回 1 MB 一次打穿窗口。按准入条件二，这一层**正常永不触发**，不承担省 token 的指标。

要点：
- 触发时必须"工具感知"，不能盲截：`Read` 知道 path/offset，给出可直接照做的续读指引；`Bash` 保留**尾部**（错误通常在末尾）而不是头部。做成工具可声明的能力，不在引擎里写死工具名清单。
- **用户侧不损失**：完整内容照旧走 `tool.Result.Output`（已有的"仅展示、永不发给模型"通道，见 `tool/result.go:8`）和 transcript，UI 该看到什么还是什么。

### L2 — 按年龄退役过期负载（确定性 / 无 LLM / 会改前缀，须批量触发）★ 收益最大

做成一条 `history.Reducer` 流水线。**准入 = 可确定性复原 且 年龄超过下限**（新鲜结果一律保持完整）：

1. **陈旧结果脱水**：年龄 > N 条消息（起始值 16）的可复原结果压到 8 KB，留可执行的续读指引：
   ```
   [... 已省略 63,182 字节；用 Read(path, offset=1200, limit=800) 取剩余部分 ...]
   ```
   这是本方案的主力：单这一条就把 §1.3 那四个大头（45.8%）收掉，且从不碰模型正在用的内容。
2. **写入类工具入参脱水**：`Write`/`Edit` 成功且已陈旧后，把历史里那条 `tool_use` 的 `content` 换成存根（`<正文已省略：9,822 字节已写入 path>`）。模型不需要回看自己刚写的东西；真要看就 Read 文件。**仅在结果已知成功后执行**，且由工具声明"我的入参可从磁盘复原"，不硬编码工具名。
3. **被取代的读取折叠**：按工具自己声明的 `Identity`（如 `Read:spec.md@0+2000`）为键，同一观测的旧结果折叠为指针。这条同时让"跟进续读指引"变得廉价且幂等 —— 重读会把旧副本折叠掉，不会双份计费。

**原计划的第 4 条"重复结果归并"已放弃**（实施时按实测数据推翻）：整份会话里完全相同的结果加起来只浪费 6,029 字节（≈1%），其中有意义的那部分（`spec_lock.md` 同范围重复读 4 次）已被上面第 3 条的 Identity 折叠覆盖；剩下的是 `"File written."` ×16、权限拒绝 ×11 这类几十字节的短串。把它们折成指针换不到 1% 的收益，却要让模型面对"我那次写入到底成没成"的歧义 —— 负收益，不做。

### L3 — 回合内压缩（本案的真正架构修复，需要 LLM，兜底层）

把 `internal/compaction` 的计量单位从**回合**推广为**段（segment）**：一个段是"一个用户回合" **或** "一对 assistant(tool_use)/tool(tool_result)"。后者本身就是自包含的，现有 `pairedClean` 的配对校验语义可直接复用，因此可以安全地把一个回合内**较早的若干轮迭代**替换成摘要，而不产生孤儿 tool_use。

- 摘要以**助手文本消息**的形式插在该回合的用户消息之后，再接保留的近期迭代 —— 角色交替与工具配对都仍然合法（assistant 文本后接 assistant/tool 对，Anthropic 与 OpenAI 两条路径都接受）。
- 触发：每轮迭代用 L0 的估算值判断；带**滞后**（一次压到预算的 ~50%，避免压完立刻又越线）和**每回合频次上限**（回合内摘要调用要稀有）。

### L4 — 修掉让问题溜过去的回合粒度默认值

- **保留窗口改为按预算驱动，而不是按个数**：保留"能装进预算 X% 的最近若干段"，下限 1 段。`DefaultKeepRecentTurns = 4` 降级为下限兜底，不再是规则本身 —— 编码代理的 4 个回合可以是 500 KB。
- `MaxHistoryMessages` 的语义（不保护当前回合）要在文档和设置页文案里讲清楚：它是消息数闸门，**不是**上下文预算控制。L3 上线后它基本让位。

### L5 — 委派给只读子代理，从源头不进上下文（★ 提到 P0，唯一"移除"而非"压缩"的措施）

本案 277 KB（45.8%）是**技能参考文档被整篇读进主线程**。这部分交给只读子代理后变成一份 ~5 KB 报告 —— **零丢失风险，因为没有任何截断，大块内容根本不进主线程**。这比任何压缩都更优。

**机制已经具备，问题是没被用起来。** 现状核实：

- `internal/subagent/default.go:22` 已有 `readOnlyTools = {Read, Glob, Grep}`；五个内置代理（code-explorer / code-reviewer / planner 只读，debugger 带 Bash，general-purpose 全继承）。
- 本案会话的工具清单里 **`Task` 在列**，系统提示词甚至明写 *"Prefer delegating well-scoped, read-heavy investigations to keep your own context lean."*
- **模型依然在主线程读了 277 KB。**

原因（这才是真发现）：

1. 五个代理的描述全部**面向代码库**。本次任务是"读 PPT 技能的参考文档产出设计规格"，没有任何代理宣称能干这个。
2. 更决定性的：**这些读取是技能自己的指令驱动的** —— ppt-master 的 `strategist.md` 让模型去读那些 references。系统提示词里一句泛泛的"优先委派"，压不过刚加载进来的、明确的技能工作流。

所以要做三件事：

- **补一个面向文档调研的只读代理**（`researcher`：`Read`/`Glob`/`Grep`，"读大量文档/参考资料，产出自包含结论"），填上目录空缺。
- **技能编写约定**：工作流需要读多份大参考文档的技能，必须写明"把调研阶段委派给只读子代理，按其报告行动"。这是让 277 KB 根本不进来的唯一办法。
- **确定性兜底**：某技能的参考文档树体积超过阈值时，`Skill` 工具结果里直接附上委派建议。
- 配套：**技能渐进式加载** —— SKILL.md 只回简短索引（本案它自己就 66 KB），references 按需在用到的那一刻再读。

### L6 — 让它可见，而不是事后惊讶

- context-audit 记录**增补 L0 估算值与分类占比**（就是本文第 1.2/1.3 节的分析，产品化掉），下次诊断一眼可见，不用再写 Python。
- 桌面 ctx 进度条改为**按迭代实时**刷新（现在读的是回合结果的 usage）；压缩发生时给出提示与省下的 token 数。

### 明确不做（避免过度工程）

**不做"上下文管理智能体"**（即让一个 LLM 每轮决定丢什么留什么）。致命缺陷：**一个上下文管理智能体必须先加载上下文才能管理它** —— 要问它"哪些能丢"，就得把正想省掉的 140K tokens 喂进去。若只喂元数据（工具名、路径、体积、年龄），那说明元数据已经够了，这就是一条确定性规则，不是判断题。两头都不成立。此外它不可测、最坏情况无界、错判是静默丢失，且每轮都在关键路径上（花 token 与延迟去省 token）；而 96% 的膨胀靠 `(工具, 路径, 年龄)` 机械可判，不需要智能。

**LLM 的正确用法是 L3 的离散摘要**：那里确实需要理解（把几十轮迭代压成"决定了什么、现在什么状态"），触发稀有，且输出是加法（事实按构造保留）。以及 L5 的委派 —— 用子代理**承接调研**，而不是用它**管理上下文**。

其余：

- 不引入按模型的真实 tokenizer（估算+校准足够；`approxCharsPerToken` 已是既有先例）。
- 不做 history 的向量库 / RAG 检索。
- 不做基于 embedding 的语义去重（L2 的确定性键值去重足够）。
- 不给 OpenAI 兼容路径补 `cache_control` 管线（该端点是自动前缀缓存，补了没用）。

## 四、量化收益（在这份真实会话上模拟）

对最终那次请求的 history 部分（140,721 est. tokens）逐档模拟。**所有档位都遵守两条准入条件**：只脱水可复原内容、只脱水陈旧内容。

| 措施 | est. tokens | 占基线 |
| --- | --- | --- |
| 基线（今天） | 140,721 | 100% |
| L1 单独（入库 64 KB 高位防护） | 132,890 | 94.4% |
| **L2 单独**（陈旧 >16 条脱水到 8 KB + 写入参脱水） | 48,914 | **34.8%** |
| L2 更激进（陈旧 >8 条脱水到 4 KB） | 36,766 | 26.1% |
| **L5 单独**（调研阶段委派只读子代理） | 42,444 | **30.2%** |
| **L5 + L2** | 20,857 | **14.8%** |

读法：

- **L1 只值 5.6%** —— 印证它是防护层，不是省 token 的手段，指标不该压在它身上。
- **L2 一层就到 34.8%**，零额外 LLM 调用、零丢失风险（只碰可复原且陈旧的内容）。
- **L5 一层到 30.2%**，而且是**移除**而非压缩 —— 那 90K tokens 的参考文档根本不进主线程，连"要不要重读"的问题都不存在。
- **两者叠加 14.8%**（140.7K → 20.9K，约 6.7 倍）。二者不重叠：L5 管"不该进来的"，L2 管"进来了但已经过期的"。
- L3 的价值不在再省一截，而在**把曲线压平** —— 本案 47 次请求单调爬升、后 44 次持续越线；L3 保证它在预算内震荡，而不是一路顶到窗口上限。

（另有系统提示词 + 工具 schema 约 5,388 tokens 为常量，未计入上表。）

引擎改动全在 `../agentloop`；桌面外壳只需要设置项与 UI 呈现。按 CLAUDE.md：引擎须**先打 tag**，再升三个模块的 require，CI 才够得着（CI 一律 `GOWORK=off`）。

### 实施中相对原方案的三处修正

1. **L2 的第四个 pass（重复结果归并）放弃** —— 实测只值 1%，且有意义的部分已被 Identity 折叠覆盖，理由见 §三 L2。
2. **触发与保留窗口统一为同一度量。** 原设计里触发用 provider 回报的 `InputTokens`、窗口用本地估算。实施时发现这会产生一个和原始 bug 同类的故障：两者尺度不一致时，窗口判定"全都装得下"而触发条件持续满足 —— **压缩每回合都跑、什么都不缩**。改为两处都走校准后的本地估算（provider 计数只用于校准与显示），失配在构造上不可能发生。
3. **`KeepRecentTurns` 在预算模式下不再作为下限。** 一度把它当兜底下限，但"至少保留 4 个回合"正是原始 bug 本身（4 个重量级回合可以超过整个预算）。现在有 Sizer 时下限是 1 段，无 Sizer 时才回落到计数。

### 补做：按迭代实时刷新 + 超 80% 立即总结再继续

`internal/repl` 把原来的 `maybeCompactInTurn` 改为 `contextControl`，每轮迭代做三件事：**测量 → 上报 → 超阈值就整理**。

- **实时刷新**：新增引擎回调 `StreamContextUsage(contextTokens, maxContextTokens, iteration)` → `protocol.EventContextUsage`（`context:usage`）→ 前端 `use-conversation` 订阅刷新 ctx 条。整理生效后会**再上报一次**，所以进度条能看到"涨上去"和"掉下来"两段，而不是数字凭空下降。
- **立即生效**：原来的"每 4 轮迭代才检查一次"（`inTurnControlInterval`）是错的 —— 越过 80% 后最多要再发 3 次超预算请求才动手。现已改为**每轮都测**，越线当轮即整理（先无损脱水，仍超则总结）后继续。
- **退避改为按进度**：需要限流的其实是相反的情况 —— 历史里有压不动的东西（一整段必须原样保留的巨大迭代）时，每轮重试只会白烧一次总结请求和一次缓存未命中。现在只在"某次整理确实没能压到阈值以下"时记下当时的占用，等历史再长出 `inTurnControlRetryGrowth`(8k tokens) 才重试。**首次不受任何延迟。**
- ctx 条文案同步纠正：旧文案写"发送一条消息后即为精确值"，但新数字始终是校准后的估算（与引擎判据同源），不会变成 provider 精确值；`≈` 的含义也从"尚未拿到精确值"改为"尚未按当前模型校准"。

### 遗留

- `MaxToolResultBytes` 只在 `engine.Config` 暴露，未接 `settings.toml` 与桌面设置页（默认值已武装，正常无需调整）。
- L2 的两个阈值（`staleAfterMessages=16`、`staleResultBytes=8KB`）取的是保守起始值。上线后应看 L6 的 audit 数据里真实的重读率，再决定是否收紧到 8 条 / 4KB（模拟收益 26.1%）。
