# Changelog

All notable changes to runcode will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project intends to follow [Semantic Versioning](https://semver.org/) from v1.0 onward.

## [Unreleased]

### Added

- Cobra CLI entry point with `version` and a minimal provider-backed `chat` command.
- TOML configuration files: project-level `runcode.toml` (discovered by walking up from the working directory) and user-level `config.toml` (under `os.UserConfigDir()/runcode/`), with precedence flag > env > project file > user file > default. Credentials (`api_key`/`auth_token`) are only honored from the user-level file; any in a project file are ignored.
- `runcode config` command that prints the effective configuration, the loaded config-file paths, and whether credentials are set (credential values are never printed).
- Full session history persistence to `<workspace>/.runcode/sessions/<id>.jsonl` (one complete `llm.Message` per line), enabled by default. `--resume <id>` restores and continues a saved session; `--continue` resumes the most recent one; `--no-session` (or `RUNCODE_SESSION_PERSIST=off`) disables persistence. The on-disk history is append-only and loss-less, kept separate from the sanitized transcript.
- SQLite transcript backend and a `runcode transcript` search/browse command. Running with `--transcript sqlite` (or `RUNCODE_TRANSCRIPT=sqlite` / `transcript = "sqlite"`) records each successful turn's sanitized `TurnRecord` into one indexed database at `<workspace>/.runcode/transcripts.db` — the full record JSON for fidelity, plus denormalized columns (session, time, model, user/assistant text). `runcode transcript list` summarizes recorded sessions (turn count, recency, model); `runcode transcript search <query>` returns matching turns newest-first (case-insensitive substring over user/assistant text, with `--session` to scope and `--limit` to cap). LIKE wildcards in a query are escaped so they match literally. Read commands never create a database — an absent one prints how to enable recording. The transcript stays the sanitized audit log (whitelisted fields), distinct from the loss-less session history that `runcode sessions` reads.
- SQLite session backend, selectable via `--session-backend sqlite` / `RUNCODE_SESSION_BACKEND` / `session_backend` (default `jsonl`, unchanged). Session history is abstracted behind a `sessions.Backend` interface (writable per-session `Store` plus `LoadHistory`/`List`/`Describe`/`Latest`) with two implementations: the original one-`.jsonl`-file-per-session store, and a single indexed SQLite database at `<workspace>/.runcode/sessions.db`. The SQLite backend stores each message's exact JSON (so resume round-trips identically) alongside denormalized role and user-text columns, so `List`/`Describe` answer turn counts and previews with indexed SQL instead of scanning every file. The driver is pure-Go (`modernc.org/sqlite`, no CGo), schema is versioned via `PRAGMA user_version` for forward migrations, and appends are transactional and mutex-serialized. `runcode sessions` and the TUI picker honor the configured backend (`runcode sessions --backend sqlite ...`).
- Session browsing and resume discovery, so a session id no longer has to be remembered. A reusable `sessions.List`/`Describe` metadata API (a single streaming pass per file: id, mod time, size, message count, user-turn count, and first/last user-prompt previews) backs two front ends: a `runcode sessions` command (`list` numbers saved sessions newest-first with a relative age, turn count, and preview; `show <id|number>` prints a bounded, readable rendering of the conversation — user/assistant text, tool calls noted by name, tool results as short snippets), and an interactive startup picker for `runcode tui --pick` that lists saved sessions (plus a "Start a new session" row) and resumes the chosen one. The picker is opt-in via `--pick`, so a plain `runcode tui` still starts fresh.
- Context compaction: with `--max-context-tokens` / `ANTHROPIC_MAX_CONTEXT_TOKENS` / `max_context_tokens` set, once a turn's input tokens approach the budget the oldest turns are summarized into a single leading message (via the provider) while recent turns are kept verbatim. Compaction is incremental: an existing summary is carried forward verbatim and only the newly aged-out turns are summarized and appended, so already-condensed facts never pass through the model a second time (repeated re-summarization is what silently drops earlier facts). The summary is only fully re-summarized once its body outgrows a character budget derived from the token budget. Compaction touches only the in-memory working set; the on-disk history stays complete and can always recompute it. The summarizer renders the aged-out turns to a plain-text transcript (tool calls noted by name, tool results as a bounded snippet) and summarizes that as a single user message, so the summary request never carries `tool_use`/`tool_result` blocks — those require the tools to be declared and are rejected by Anthropic and several OpenAI-compatible endpoints, which previously made compaction fail on every tool-using session. The Anthropic provider also now merges consecutive same-role messages, so the compacted history (a summary user message immediately before the first kept user turn) satisfies the API's strict user/assistant alternation.
- `pkg/llm` `Message`/`ContentBlock`/`ImageSource` now carry JSON tags so session history serializes to a stable, compact format that round-trips faithfully.
- `chat --loop` for process-local in-memory multi-turn sessions, with `/clear` to reset loop history.
- Provider-neutral LLM model in `pkg/llm`, including messages, content blocks, tool specs, streams, usage, and cache-control hints.
- Anthropic streaming provider skeleton using the official Anthropic Go SDK.
- OpenAI-compatible streaming provider (`--provider openai` / `RUNCODE_PROVIDER=openai`) that speaks the Chat Completions wire protocol directly over HTTP/SSE — no vendor SDK — so it also drives compatible endpoints (vLLM, Ollama, llama.cpp, LM Studio, and gateways such as a self-hosted qwen). It maps neutral messages to OpenAI roles (system merge, `tool_use` → `tool_calls`, `tool_result` → `tool` messages, images → `image_url`), reassembles streamed `content`/`tool_calls` deltas into block-structured events, and reports usage and stop reasons. The bearer credential is optional so unauthenticated local endpoints work; `--base-url` should point at the API root that serves `/chat/completions`.
- Prompt cache hints are now derived from the provider: `repl.NewSession` reads `llm.Provider.Capabilities().SupportsCacheControl` and the system-prompt assembler marks static sections with ephemeral cache control only when the provider supports it. Anthropic keeps its prompt caching; OpenAI-compatible providers no longer get no-op cache metadata. (Automatic compaction-budget inference from a provider's context window remains future work, since the capability is currently sourced from the CLI flag and cannot be derived for arbitrary compatible-endpoint model names.)
- Provider request retries: transient failures during connection setup (network errors, 429, and 5xx/529) are retried with capped exponential backoff that honors a numeric `Retry-After`. The OpenAI-compatible provider retries inside its HTTP transport — only the request-establishment phase, never mid-stream once the body is flowing — and the Anthropic provider enables the SDK's built-in retries. A cancelled/timed-out context and non-retryable client errors (4xx other than 429) are surfaced immediately. The retry count is configurable via `--max-retries` / `RUNCODE_MAX_RETRIES` / `max_retries` (0 = default, negative = disabled).
- Public tool SDK boundary in `pkg/tool`, including tool context, schema, events, result content, metadata, and `is_error` support.
- Built-in tools registered through `tools.Builtins()`:
  - `Read`
  - `Write`
  - `Edit`
  - `Glob`
  - `Grep`
  - `Bash`
  - `TodoWrite`
  - `WebFetch`
- `Read` tool with line-numbered output, offset/limit support, output bounds, and complete/partial read metadata.
- `Write` tool for workspace file creation and fresh-read overwrites.
- `Edit` tool for fresh-read exact string replacement and replace-all edits.
- `Glob` tool for workspace file discovery with slash glob semantics and `**` support.
- `Grep` tool for workspace regexp search with path/glob filtering and bounded output.
- Minimal `Bash` tool with workspace cwd, no stdin, timeout, stdout/stderr capture, output truncation, and `is_error` result semantics for non-zero exit or timeout.
- `TodoWrite` tool: the model records its current task list by passing the complete list each call (replacing the previous one). Each item has content, a status (pending/in_progress/completed), and an activeForm; the tool validates the list (non-empty, valid statuses, at most one in_progress), renders a checklist, and emits a progress event for the UI. It is side-effect-free and classified as a new `manage` permission operation that is allowed without approval (no files or commands). Registered in `tools.Builtins()` and exposed to the model and prompt automatically.
- `WebFetch` tool: fetches an http(s) URL (GET, with timeout, a 5 MiB body cap, and a redirect limit that refuses non-http(s) schemes) and returns its text — HTML is reduced to plain text (script/style/head dropped, block elements becoming line breaks), other text/JSON/XML is returned as-is, and binary content is rejected. It is modeled as a new `network` permission operation that always requires approval (so safe mode denies it); the approval shows the target host (never the full URL), and "allow for session/project" can be granted per host. Verified live against `example.com`.
- Finite ReAct session controller in `internal/repl` with tool-use iteration, tool-result conversion, max-iteration protection, in-memory history, and optional reasoning classification.
- Unified permission boundary in `internal/permissions`, including action/resource/risk modeling, resolver, policy, safe mode, interactive approval, command classification, and sanitized approval summaries.
- Permission-aware executor that records permission decisions and returns permission denial, unknown tools, and recoverable tool runtime errors as error tool results.
- Shared path resolution and fresh-read gates in `internal/toolpath`.
- Telemetry foundation in `internal/telemetry`, including event model, no-op recorder, JSONL recorder, bounded async recorder, memory recorder, and trace/turn/request IDs.
- `--telemetry off|jsonl` and `RUNCODE_TELEMETRY` support for CLI chat.
- System prompt assembler in `internal/prompt`, with static/dynamic cache boundary, tool descriptions, environment section, permission-mode guidance, memory/project context slots, and reasoning guidance.
- Project context loader for `RUNCODE.md` / `CLAUDE.md`, wired into `chat` prompt construction with bounded reads and truncation.
- Opt-in JSONL transcript recording with `--transcript jsonl` / `RUNCODE_TRANSCRIPT=jsonl` and optional `--session-id` / `RUNCODE_SESSION_ID`.
- Minimal Bubble Tea `runcode tui` MVP with a Claude Code-style bottom status area, cumulative context token and thinking-mode indicators, conversation viewport, single-line input with top and bottom dividers, streaming assistant Markdown rendering, tree-style tool progress cards with safe file summaries, and `/help`, `/clear`, `/status`, `/exit`.
- TUI slash commands are now driven by an extensible registry: each command (name, aliases, summary, handler) is registered in one place, and parsing, alias resolution, dispatch, and help text are all generated from it — adding a command no longer means editing a parse switch, a dispatch switch, and a hand-written help string. Built-ins are `/help`, `/clear`, `/status`, `/mode`, `/compact`, `/cost`, and `/exit` (alias `/quit`); the registry is the base for future `/model`.
- `/compact` slash command: summarizes the oldest turns of the current conversation on demand (regardless of the token budget) and reports the before/after message count, backed by a new `Session.Compact` and a `Compact` service method. Only the in-memory working set is touched; the on-disk session log stays complete. Available in the TUI.
- `/cost` slash command and token cost tracking: cumulative input/output tokens are summed across the session's turns; `/cost` shows them and, when `--input-price`/`--output-price` (or `input_price`/`output_price` in config, per million tokens) are set, an estimated cost. Compatible endpoints have no standard pricing, so it reports tokens only until prices are configured.
- Built-in model pricing table (`internal/cost`): when no explicit price is set, the per-token price is looked up from a small built-in table by model name (case-insensitive, longest-prefix match — so dated ids like `claude-opus-4-8-20251231` still match), covering the Claude 4.x family and common OpenAI models. The table is a convenience default and clearly attributed: `/cost` notes "approximate built-in pricing for <model>" and `runcode config` tags the price as `(built-in pricing for <model>)`, `(explicit)`, or `(unset)`. An explicit price always wins (including an explicit `0` for a free local endpoint, which is distinguished from unset and is never auto-filled), and an unknown model — e.g. a self-hosted endpoint — stays unpriced. Prices are approximate public list prices and should be set explicitly for billing-grade accuracy.
- `/mode` slash command for runtime permission-mode switching: `/mode safe|interactive` flips approval behavior without restarting. `permissions.Service` is now mode-aware — an interactive authorizer is always built (even when starting in safe mode) so safe can be widened to interactive at runtime, and concurrency/approval availability track the current mode. The status line reflects the new mode. Switching to interactive requires an approver; sensitive actions are still approved individually. Available in the TUI.
- TUI slash command menu: typing `/` opens a menu of matching commands above the input (generated from the registry, so it always lists exactly the available commands). It filters as you type; arrow keys navigate, Tab completes the name ready for arguments, Enter runs the highlighted command, and Esc closes it.
- Multi-line TUI input with history recall: the input is now a `textarea` that grows with its content (up to a cap, then scrolls internally) and shrinks back after a turn. Enter still sends; `alt+enter`/`ctrl+j` insert a newline. ↑/↓ recall previously submitted inputs (a readline-style history that de-duplicates consecutive entries and preserves the live draft while browsing), and inside a multi-line draft they move the cursor between lines, only crossing into history at the first/last line. Viewport scrolling moved to PgUp/PgDn, Home/End, and the mouse wheel. The history buffer is an isolated, unit-tested component decoupled from the widget; the bottom chrome height is still derived from a single source so layout stays consistent as the input grows.
- Model Context Protocol (MCP) client integration. runcode can connect to MCP servers and expose their tools to the model as `mcp__<server>__<tool>`. Implemented from scratch (no vendor SDK) as a transport-agnostic JSON-RPC 2.0 layer over two transports: **stdio** (a local server launched as a direct subprocess — no shell — with bounded framing and stderr diagnostics) and **Streamable HTTP** (POST with single-JSON or SSE responses and `Mcp-Session-Id` continuity). A Manager connects every configured server tolerantly (a server that fails to start/handshake/list is reported and skipped, never aborting the session), aggregates and de-duplicates their tools, and is closed with the session. Servers are configured under `[mcp.servers.<name>]` in the **user-level** config only (a project file can never inject a server, since that would launch a subprocess just by being opened), support stdio/http transports, an `enabled` flag, and `${VAR}` expansion so secrets stay in the environment. MCP tools are gated by a new **external** permission operation: every call requires approval (safe mode denies it), the approval shows the server and tool, and "allow for session/project" remembers a grant per server+tool (rendered/removable via `runcode permissions`). `runcode config` lists the configured servers (names and transports only).
- MCP resources: when a connected server advertises the resources capability, two built-in tools are exposed — `ListMcpResources` (lists each server's resources by uri/name/description, optionally filtered to one server) and `ReadMcpResource` (reads a resource's contents by server + uri). Both reuse the existing JSON-RPC layer (`resources/list` with pagination, `resources/read`); inline text passes through while binary (blob) contents are noted as a placeholder. Like server tool calls they are **external** operations requiring approval (safe mode denies them); a read grant is remembered per server+uri and a per-server list grant via a list sentinel, while listing across all servers is approved each time. The tools appear only when at least one connected server supports resources, in both `chat` and the TUI.
- MCP prompts: when a server advertises the prompts capability, two built-in tools mirror the resource tools — `ListMcpPrompts` (lists each server's prompt templates with their arguments) and `GetMcpPrompt` (renders a template by server + name with a string-argument map, returning its messages). They reuse `prompts/list` (paginated) and `prompts/get`, are classified as external operations requiring approval (a get grant is remembered per server+prompt), and appear only when a server supports prompts.
- MCP roots: runcode now answers server-initiated requests. It advertises the `roots` capability during initialize when it has roots and responds to `roots/list` with the workspace as a `file://` root, so a server (e.g. a filesystem server) can learn the directory runcode operates in; it also answers `ping`. This required teaching the JSON-RPC connection to dispatch server→client requests (routing on the presence of a method so a server's request ids never collide with our outstanding-call ids) and write responses.
- MCP sampling: a server may request a model completion via `sampling/createMessage`, which runcode serves with its own provider. Because this spends the user's model on a server's behalf, it is **off by default** and opt-in via `--allow-mcp-sampling` / `RUNCODE_ALLOW_MCP_SAMPLING` / `[mcp] allow_sampling` (user-level config only); the sampling capability is advertised, and such requests are served, only when enabled, and **safe mode always refuses** regardless. Enabling it is the pre-authorization — there is no per-request prompt yet. runcode never shares its own conversation: only the server-supplied messages and system prompt are sent, the request declares no tools, `maxTokens` is bounded, and `modelPreferences`/`includeContext` are ignored. The provider-backed sampler lives in `repl` and is injected through `mcp.Open`'s options so the protocol layer keeps no provider dependency. `runcode config` shows the sampling state (`on` / `off` / `off (denied in safe mode)`). MCP resource templates and subscriptions remain out of scope; per-request interactive sampling approval is future work.
- Hooks: user-configured commands that run at lifecycle events so policy, auditing, or context injection can be added without changing runcode. Three events are supported: **PreToolUse** (after a tool is authorized, before it runs — a non-zero exit blocks the tool and its output is returned to the model), **PostToolUse** (after a tool runs — its output is appended to the result as feedback), and **UserPromptSubmit** (when a prompt is submitted — a non-zero exit rejects the prompt, otherwise the hook's output is injected as additional context for the turn). Hooks are configured as `[[hooks]]` entries (`event`, `matcher`, `command`, `timeout_ms`) in the **user-level** config only — like MCP servers, a project file can never register a hook, since hooks run arbitrary commands. The command is run directly (no shell) with the event payload as JSON on stdin; output is bounded and sanitized before it reaches the model. A hook that *runs and exits non-zero* is a deliberate block, while one that *fails to run* (missing binary, timeout) fails open with a warning so a broken hook does not brick the session. `runcode config` lists the configured hooks as `event:matcher` without printing their commands. Tool hooks integrate at the executor (so they cover builtin, MCP, and skill tool calls); session lifecycle events (SessionStart/End), structured-JSON hook decisions, and matcher globs/regex are out of scope for now.
- Skills: reusable workflows loaded from convention directories with progressive disclosure. A skill is a directory holding a `SKILL.md` whose frontmatter declares a `name` and `description` and whose body is detailed instructions. Skills are discovered from `<userConfigDir>/runcode/skills/` (user-level) and `<workspace>/.runcode/skills/` (project-level); a user skill shadows a project skill of the same name. To keep context cheap, only a compact **catalog** (each skill's name and description, with a `[project]` tag for workspace skills) is injected into the system prompt; the full body is disclosed on demand when the model calls the new built-in `Skill` tool with a skill name. The `Skill` tool only returns in-memory instruction text — it launches nothing and touches no files — so the permission layer classifies it as side-effect-free management (allowed without approval, even in safe mode). Loading is tolerant: a malformed or oversized skill is skipped with a sanitized warning rather than breaking the session, bodies are size-capped, and a UTF-8 BOM is tolerated. Project skills are honored (so teams can share workflows in-repo) but are attributed as `[project]` since their text enters the prompt. `runcode config` lists the loaded skill names (project ones tagged) without printing any body. Available in both `chat` and the TUI. Executable skills (a skill declaring its own tools/commands), semantic matching, and remote skill registries are out of scope for now.
- Sub-agents: the main agent can delegate a focused, self-contained task to a specialized sub-agent via the new built-in `Task` tool. A sub-agent is a definition loaded from convention directories — `<userConfigDir>/runcode/agents/*.md` (user-level) and `<workspace>/.runcode/agents/*.md` (project-level) — whose frontmatter declares a `name`, `description`, an optional `tools` allowlist (comma/space separated; omitted or `*` inherits every delegatable tool), and an optional `model` override, and whose body is the sub-agent's system prompt. A built-in `general-purpose` agent is always available, and a user/project definition can shadow a same-named builtin. Like skills, only a compact **catalog** (each agent's name and description, `[project]`-tagged for workspace agents) is injected into the prompt; the model delegates by calling `Task` with a `subagent_type`, `description`, and a standalone `prompt`. Each delegation runs a child `repl.Session` with its own persona prompt, the restricted tool set, a fresh read-set, and its own model, then returns the sub-agent's final message as the tool result. Sub-agents never receive the `Task` tool, so delegation is exactly one level deep (no nesting). They share the parent's permission service — so safe/interactive semantics and PreToolUse hooks apply uniformly and every child tool call is authorized individually — which makes the `Task` wrapper itself side-effect-free management (allowed without approval; the real gating is on the child's tool calls). Child sessions are ephemeral: their transcript and resumable session log are not persisted, though they record telemetry under their own trace. Sub-agent tool activity surfaces to the parent as concise progress lines attributed to the `Task` call. Several `Task` calls in one turn fan out and run concurrently, bounded by a configurable concurrency cap (and automatically serialized under interactive permission mode, since concurrent approval prompts cannot interleave coherently). Loading is tolerant: a malformed or oversized definition is skipped with a sanitized warning, and a `README.md` in an agents directory is treated as documentation rather than a malformed agent. `runcode config` lists the available sub-agents (user/project ones tagged). Project sub-agents are shared in-repo (`.gitignore` tracks `.runcode/agents/`, mirroring `.runcode/skills/`), and ready-to-copy templates ship in `examples/agents/`. Available in both `chat` and the TUI. Cross-provider sub-agents and per-agent context budgets are out of scope for now.
- Memory: a persistent notebook the assistant maintains across sessions, separate from project context (`RUNCODE.md`/`CLAUDE.md`). The model saves a durable fact — a user preference, project convention, or recurring gotcha — with the new built-in `Remember` tool, and saved memories are injected into the system prompt at the start of later sessions. Memory has two scopes, each a Markdown file of one-line bullet entries: **project** (`<workspace>/.runcode/memory.md`, the default — under git-ignored `.runcode/`, so it stays a local notebook rather than a committed file) and **user** (`<userConfigDir>/runcode/memory.md`, via `scope: "user"`, shared across projects). `Remember` only ever writes these fixed runcode-owned files (it never takes a path), so it is classified as side-effect-free `manage` and allowed without approval — note-taking works even in safe mode; equivalent facts are de-duplicated case-insensitively. Sub-agents read memory but are not granted `Remember`, so only the main session writes it. Memory fills the assembler's previously-unused `Memory` prompt section, loaded once at startup; `runcode config` reports the per-scope entry counts without printing any text. Per-turn live reload, editing/forgetting individual entries, and semantic recall are out of scope for now.
- `/model` slash command for runtime model switching: `/model <name>` changes the model used for subsequent turns without restarting (`/model` with no argument shows the current one). The switch is in-memory only — it is not written to config files. `repl.Session` now owns the model behind an `RWMutex` with `Model()`/`SetModel()` accessors so a turn goroutine and the UI loop never race on it; the command refuses to switch mid-turn (like `/clear` and `/compact`) so a single turn always sees a stable model, and an empty model is rejected. The status line reflects the new model immediately. Available in the TUI.
- `runcode permissions` command to manage the persisted permission rules in `<workspace>/.runcode/permissions.json` without hand-editing JSON: `list` numbers the persisted allow/deny rules in a readable form (every grain — network host, mutation target, command category — is parsed and shown, including the ones the interactive "allow for project" prompt writes), `remove <n>` deletes a rule by its listed number, and `clear [--allow|--deny]` empties the lists. `deny <host>` and `allow <host>` add a network rule for a host (default tool `WebFetch`) — the one key kind that is reliably typeable and matches the runtime key exactly; a deny always wins, so allowing a denied host is refused until the deny is removed. The session/persistent key format is now centralized behind `NetworkSessionKey`/`MutateSessionKey`/`CommandSessionKey` constructors plus a `ParseRule` reader (one source of truth shared by the runtime and the CLI), and `FileAllowStore` gained `Allows`/`Denies`/`DenyPersistent`/`Forget`/`ClearPersistent` for management.
- Interactive approval prompt on stderr for `--permission-mode interactive` / `confirm`.
- TUI permission modal for `--permission-mode interactive`, with allow once / allow for session / deny choices, keyboard selection, sanitized request details (tool, operation, risk, workspace-relative targets, command classification), and serialized prompts.
- Session-scope permission memory: choosing "allow for session" stops re-prompting for equivalent actions (per mutation target for Write/Edit, per command classification for Bash) for the lifetime of the process session; available in both the TUI and the CLI interactive prompt.
- Persistent permission grants: interactive approval now offers "allow for project" alongside allow once / allow for session. Project grants are written to `<workspace>/.runcode/permissions.json` (0600, gitignored) and honored across processes, keyed by the same per-mutation-target / per-command-classification grain. The file also carries a denylist that is checked before prompting — a denied action is rejected without asking, and a deny always wins over an allow. A corrupt permissions file fails fast rather than silently dropping denylist rules. Available in both the TUI modal (`[p] allow project`) and the CLI prompt (`[p]roject`).
- Rich tool output in the TUI: tool progress cards now show a bounded, sanitized output excerpt — Bash stdout/stderr (with exit/duration envelope), Grep match lines, and a Read preview — expandable with `ctrl+o`. Output is display-only and never recorded to telemetry or transcripts.
- Full unified line diff for `Edit` and `Write`, computed by a new bounded `internal/diff` package and rendered with added/removed/context styling in the tool card; binary or oversized files fall back to a summary line.
- Current implementation status document at `docs/implementation-status.md`.

### Changed

- Documentation now reflects the current minimal chat/session/tool/permission implementation instead of the original placeholder-only scaffold.
- `docs/data-flow-and-prompt.md` now describes the actual CLI -> Session -> provider -> tool -> permission flow.
- `docs/architecture.md` tracks the current implemented architecture, including `Bash` MVP and command permission classification.

### Fixed

- Tool result conversion preserves `is_error` semantics for permission denials, unknown tools, recoverable tool runtime errors, and Bash command failures.
- Permission denial tool results now include sanitized reason and final-effect details so the model can self-correct without exposing raw inputs.
- Shared line input avoids buffered stdin loss between `chat --loop` prompts and interactive approval prompts.
- Session history cloning deep-copies raw tool input and image data.
- Remembered memory entries and agent definition bodies that exceed their byte caps are truncated on a UTF-8 rune boundary instead of mid-rune, so trimming no longer leaves invalid UTF-8 (notably for CJK text).
- The TUI bounds its in-memory chat history (oldest entries are trimmed between turns, leaving a marker) so a very long session no longer grows the message buffer without limit.
- The `Task` tool rejects an over-long delegated prompt (>128 KiB) as a self-correctable `is_error` result, so a runaway generation cannot blow up a sub-agent's context.

### Security

- Workspace containment is enforced for read/search/mutation tools, including symlink escape checks.
- Write/Edit mutations require fresh complete reads before overwriting or editing existing files.
- Permission telemetry and approval prompts avoid raw paths, raw commands, tool inputs, tool outputs, file contents, credentials, and URLs.
- Bash commands are classified before execution; unknown, privileged, destructive, outside-write, and complex shell-control commands are denied before approval.
- The default `safe` permission mode does not execute approval-requiring writes, edits, or Bash commands.
- Transcript records use a whitelist schema and omit system prompts, credentials, generic tool raw input, and full tool output; enabled transcripts may still contain user prompts, assistant text, and Bash command strings.
- `WebFetch` blocks server-side request forgery: a `net.Dialer` control hook checks the resolved IP just before connect and refuses non-public addresses (loopback, RFC 1918 / ULA private, link-local including the `169.254.169.254` cloud-metadata endpoint, carrier-grade NAT, multicast, and unspecified). The check covers the initial request, every redirect hop, and DNS rebinding; no HTTP proxy is configured so the real destination IP stays visible to the check.
